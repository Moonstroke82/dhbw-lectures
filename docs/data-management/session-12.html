Checklist: Schema and Data

Model fit: every entity type and relationship of your ER model has a home — and the tables match the milestone 2 schema (or you documented why not)
Keys: every table has a primary key; weak entity types use owner key + partial key
Foreign keys: on the N side of 1:N; M:N as its own table; referential actions chosen on purpose
Normal form: no lists in a cell, no partial or transitive dependencies — or a documented reason
Constraints: NOT NULL, UNIQUE, CHECK for the business rules; dates as ISO text (YYYY-MM-DD)
Switched on: PRAGMA foreign_keys = ON in every connection; PRAGMA foreign_key_check returns no rows
Rebuildable: schema and data scripts run on an empty database without errors

Own summary based on Elmasri and Navathe (2016, Chapters 5, 9 and 14) and SQLite (n.d.-a, n.d.-d).

Checklist: Queries

Question first: write the business question in words — what does one row of the answer mean?
Path: which tables, which foreign keys? n tables → n − 1 join conditions
Missing partners: LEFT JOIN where a row may have no partner; filters on the optional table go into ON
Grouping: every SELECT column is grouped or aggregated; count(column) instead of count(*) after an outer join
NULL: IS NULL, NOT EXISTS instead of NOT IN, coalesce where "unknown" should count as 0
Levels: aggregate each 1:N path on its own level before joining
Check: predict the number of rows and one value — then compare

Own summary of sessions 8–10, based on Elmasri and Navathe (2016, Chapter 7) and SQLite (n.d.-b, n.d.-c).

Key Takeaways

•Parts A–B form one path: case → ER model → relational schema → normal form → SQL tables → queries
•A good schema has keys, foreign keys and constraints that express the business rules — and they are switched on
•A good query starts with the business question and the meaning of one row
•Most wrong results come from NULL, missing partners and aggregating on the wrong level
•Check before you trust: predict, run, compare
